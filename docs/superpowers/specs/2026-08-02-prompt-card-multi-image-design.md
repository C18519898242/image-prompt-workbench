# 提示词卡片多图展示设计

## 文档状态

- 状态：已批准设计，待实现
- 日期：2026-08-02
- 适用范围：MVP

## 1. 背景

一个提示词卡片可能对应多张示例图片。当前导入器已经能够下载同一个卡片的多张图片，但 `prompt_cards` 表只保存第一张图片路径，前端也还没有多图卡片展示能力。

本设计在不增加图片子表的前提下，为每个卡片增加图片数量，并根据现有文件命名规律恢复同一张卡片的其他图片，使列表页和详情轮播能够展示全部图片。

## 2. 目标

本次设计需要实现以下能力：

1. 一个提示词卡片支持一张或多张 JPG 或 PNG 示例图片；同一卡片默认使用同一种扩展名。
2. 数据库继续保存第一张图片路径，同时保存该卡片的图片数量。
3. 提示词卡片列表显示第一张图片，并显示图片数量。
4. 点击卡片后，在详情弹窗中使用轮播查看全部图片。
5. 图片始终完整显示，允许出现留白，不裁剪、不变形。
6. 保持现有数据库中单图卡片的兼容性。

## 3. 非目标与范围边界

以下内容不属于本次 MVP：

- 增加 `prompt_card_images` 等图片子表；
- 重复导入、去重、更新已有卡片或图片覆盖策略；
- 图片格式转换器；
- 同一卡片混合 JPG、PNG 时的完整兼容；
- 图片拖拽排序、删除、替换等管理功能；
- 独立的图片资源管理页面。

重复导入的行为保持现状，不在本任务中改变。后续需要单独设计稳定标识、文件命名和导入更新策略。

## 4. 文件命名和数据约束

示例图片沿用当前导入器的命名规则：

```text
prompt-images/0001-01.jpg
prompt-images/0001-02.jpg
prompt-images/0002-01.png
```

文件名由以下部分组成：

- 四位卡片序号，例如 `0001`；
- 两位图片序号，例如 `01`、`02`；
- 图片扩展名，例如 `.jpg` 或 `.png`。

数据库中的第一张图片路径作为封面和命名推导依据。例如：

```text
example_image_path = prompt-images/0001-01.jpg
image_count = 2
```

后端根据第一张路径中的目录、卡片序号、扩展名和 `image_count` 推导：

```text
prompt-images/0001-01.jpg
prompt-images/0001-02.jpg
```

同一个卡片默认认为所有图片扩展名一致。导入器可以比较同一卡片的图片扩展名；如果发现不一致，只打印警告并继续导入，不做格式转换，也不因为格式不一致而中断导入。此时该卡片的轮播可能无法找到部分图片，属于已知 MVP 限制。

图片顺序以来源 Markdown 中出现的顺序为准，第一张图片始终作为封面。

## 5. 数据库设计

在现有 `prompt_cards` 表中增加字段：

```sql
image_count INTEGER NOT NULL DEFAULT 1 CHECK (image_count > 0)
```

保留现有字段：

```text
example_image_path TEXT NOT NULL
```

字段职责如下：

| 字段 | 作用 |
| --- | --- |
| `example_image_path` | 第一张图片的相对路径，同时作为封面和文件命名推导依据 |
| `image_count` | 当前卡片的图片数量 |

已有数据库通过迁移增加 `image_count`，旧卡片默认数量为 `1`。不保存每一张图片的独立数据库记录。

## 6. 导入流程

导入器按以下流程处理图片：

1. 解析卡片中的全部图片 URL。
2. 按来源顺序下载图片。
3. 使用现有规则生成 `卡片序号-图片序号.扩展名` 文件名。
4. 将图片数量写入 `image_count`。
5. 将第一张图片的相对路径写入 `example_image_path`。
6. 比较同一卡片的图片扩展名；不一致时输出包含卡片序号和扩展名的警告。

本次不引入图片格式转换。导入器仍然保留下载文件的实际 JPG 或 PNG 后缀。

## 7. 后端 API 设计

### 7.1 获取卡片列表

新增受 Bearer Token 保护的接口：

```text
GET /api/prompt-cards
```

接口返回卡片元数据和由后端推导出的图片接口地址。示例：

```json
{
  "items": [
    {
      "id": 1,
      "title": "卡片标题",
      "prompt_text": "完整提示词",
      "sort_order": 1,
      "category_ids": [],
      "image_count": 2,
      "images": [
        {
          "index": 1,
          "url": "/api/prompt-cards/1/images/1"
        },
        {
          "index": 2,
          "url": "/api/prompt-cards/1/images/2"
        }
      ]
    }
  ]
}
```

后端不要求前端了解文件命名规则。前端只使用接口返回的图片地址。

### 7.2 获取单张图片

新增受 Bearer Token 保护的接口：

```text
GET /api/prompt-cards/{card_id}/images/{image_index}
```

后端根据卡片的 `example_image_path` 和 `image_count` 推导目标文件，并执行以下校验：

- 卡片存在；
- 图片序号从 `1` 开始且不超过 `image_count`；
- 推导出的文件路径位于图片目录内；
- 文件存在且是允许的图片文件。

不满足条件时返回合适的 404 错误，前端显示图片占位状态，但不影响标题和提示词展示。

当前项目使用 Bearer Token 鉴权，浏览器的 `<img>` 标签不会自动添加 `Authorization` 请求头。因此前端需要使用 `fetch` 携带 Token 获取图片二进制，再创建浏览器对象 URL 展示。对象 URL 在组件卸载或图片切换后及时释放。

## 8. 前端交互设计

### 8.1 卡片列表

登录成功后显示提示词卡片浏览页。

每张卡片包含：

- 第一张示例图片；
- 图片数量标记，例如“共 3 张”；
- 卡片标题；
- 提示词摘要；
- 点击区域。

图片使用统一展示区域和 `contain` 方式完整显示。图片比例不一致时保留留白，使用中性背景填充，避免卡片高度跳动。

### 8.2 卡片详情弹窗

MVP 默认使用居中弹窗，不跳转独立页面，以保留用户在列表中的浏览位置。

弹窗包含：

- 固定高度或最大高度的图片展示区域；
- `contain` 图片适配方式；
- 左右切换按钮；
- 当前序号和总数，例如 `2 / 3`；
- 图片缩略图导航；
- 卡片标题；
- 完整提示词；
- “立即尝试”或填入生成区域的操作入口。

图片切换时展示区域尺寸保持稳定，不因为横图、竖图切换而造成页面跳动。图片不得被裁剪或拉伸。

## 9. 错误和边界行为

- 没有图片的卡片仍然视为导入错误，沿用现有校验。
- 图片下载失败沿用现有导入错误处理。
- 同一卡片 JPG、PNG 混用时只打印警告，不转换、不阻止导入。
- 图片文件缺失时，图片接口返回 404，卡片仍展示标题和提示词。
- 旧数据库记录的 `image_count` 默认是 `1`。
- 重复导入导致的重复卡片和文件冲突不在本次处理范围内。

## 10. 测试和验收标准

### 后端测试

- 旧表迁移后已有卡片的 `image_count` 为 `1`。
- 导入一张图片的卡片时数量为 `1`。
- 导入两张 JPG 图片的卡片时数量为 `2`，文件名分别为 `01` 和 `02`。
- 导入两张 PNG 图片的卡片时数量为 `2`。
- 同一卡片扩展名不一致时会输出警告，但导入流程不会因为该警告失败。
- 卡片列表接口返回正确的 `image_count` 和图片接口地址。
- 图片接口可以返回第 1 张和后续图片，并拒绝超出数量的序号。
- 未携带有效 Token 时，卡片接口和图片接口返回 401。

### 前端测试

- 卡片显示第一张图片和图片数量标记。
- 点击卡片后打开详情弹窗。
- 轮播可以切换全部图片并显示当前序号。
- 图片加载失败时显示占位状态，标题和提示词仍然可见。
- 轮播图片使用完整显示策略，不依赖图片原始尺寸改变布局。

### MVP 验收

当数据库中存在以下记录和文件时：

```text
example_image_path = prompt-images/0001-01.jpg
image_count = 2

prompt-images/0001-01.jpg
prompt-images/0001-02.jpg
```

用户可以在列表看到第一张图片和“共 2 张”，点击卡片后在弹窗中完整查看两张图片，图片比例不同也不会被裁剪或拉伸。

## 11. 后续扩展

后续如需支持混合格式、图片替换、重复导入和稳定资源标识，应重新评估当前命名约定，并考虑以下方向：

- 导入阶段统一转换图片格式；
- 使用独立图片表保存每张图片的路径和 MIME 类型；
- 为导入来源和卡片建立稳定标识；
- 为每次导入使用独立目录，避免文件覆盖。
