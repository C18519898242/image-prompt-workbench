# 提示词库卡片管理设计

## 1. 背景与目标

当前提示词库支持登录后浏览、搜索、分类筛选、排序、查看示例图，以及将提示词带入生成工作台。卡片数据主要通过命令行批量导入，网页端没有新增、编辑或删除入口。

本次功能为提示词库增加网页端卡片管理能力，使用户可以在不离开提示词库上下文的情况下：

- 新增提示词卡片；
- 编辑卡片标题、提示词正文和示例图；
- 批量上传、预览、移除和调整多张示例图的顺序；
- 删除没有生成历史的卡片；
- 在操作失败时保留尚未保存的输入并获得明确反馈。

## 2. 范围

### 2.1 本次包含

- 提示词库工具栏中的“新增提示词”入口；
- 卡片上的“编辑”和“删除”操作；
- 新增与编辑共用的右侧抽屉表单；
- 本地 JPG、PNG 图片的批量上传和多图排序；
- 新增、编辑、删除提示词卡片的鉴权 HTTP API；
- 文件验证、临时写入、失败清理和数据库一致性处理；
- 前后端自动化测试与现有功能回归验证。

### 2.2 本次不包含

- 分类选择、分类创建或分类管理；新建卡片的分类默认为空；
- 网络图片 URL 导入；
- WebP、GIF、SVG 等其他图片格式；
- 回收站、软删除或删除后的恢复；
- 多用户权限、操作审计和并发编辑冲突处理；
- 将生成历史中的图片直接保存为提示词示例图。

## 3. 关键决策

### 3.1 一次性表单提交

新增或编辑时，标题、提示词正文、图片顺序清单和新上传图片通过同一个 `multipart/form-data` 请求提交。后端完成全部验证后统一保存。

该方式可以避免“卡片已创建但图片只上传了一部分”的中间状态，也不需要维护临时上传会话、过期任务或孤儿上传记录，符合当前单用户、本地文件存储架构。

### 3.2 右侧抽屉

新增和编辑都使用右侧抽屉。桌面端抽屉宽度为 `40vw`，最小 480 px、最大 720 px；视口宽度不超过 768 px 时使用全屏抽屉。关闭抽屉后仍保留原提示词库的搜索、筛选、排序和滚动上下文。

### 3.3 保留现有数据库结构

继续使用 `prompt_cards.example_image_path` 记录首图相对路径，并使用 `prompt_cards.image_count` 记录图片数量。图片仍以连续编号命名，因此本次不新增数据表或字段，也不需要数据库迁移。

分类关联保持为空。现有批量导入卡片所带的分类不受影响，编辑卡片时也不修改其既有分类关联。

## 4. 用户界面与交互

### 4.1 提示词库入口

提示词库工具栏新增主按钮“新增提示词”。每张提示词卡片增加操作菜单，其中包含：

- 编辑；
- 删除。

“使用此提示词”、图片预览、搜索、筛选和排序行为保持不变。

### 4.2 新增与编辑抽屉

抽屉按以下顺序展示：

1. 标题；
2. 提示词正文；
3. 示例图；
4. 取消和保存操作。

新增时字段为空；编辑时加载当前卡片数据和全部示例图。标题和提示词正文均为必填项，去除首尾空白后不能为空。

保存期间禁用重复提交，并显示明确的保存中状态。保存成功后关闭抽屉，用接口返回的完整卡片更新列表；新增卡片按当前排序规则进入正确位置，编辑卡片保持当前搜索和筛选条件。

用户在存在未保存修改时关闭抽屉，需要二次确认，避免误丢内容。保存失败时抽屉保持打开，文本、图片预览和排序均不丢失。

### 4.3 示例图管理

示例图区域支持：

- 一次选择多张本地图片；
- 显示缩略图和文件名；
- 移除任意图片；
- 拖动调整顺序；
- 使用“前移”“后移”按钮调整顺序，保证键盘可操作性；
- 继续添加图片到当前队列。

每张卡片必须至少保留一张示例图。编辑时可以混合保留的旧图片与新上传图片，并按最终界面顺序保存。

限制如下：

- 仅接受经过内容验证的 JPG、PNG；
- 单张图片不超过 20 MB；
- 每张卡片最多 20 张图片；
- 单次请求中的图片总量不超过 100 MB。

前端在选择文件时先执行快速校验，后端执行最终可信校验。

### 4.4 删除

删除前展示二次确认，并明确说明删除后不可恢复。确认后调用删除 API：

- 卡片不存在时提示数据已不存在，并从当前列表移除陈旧项；
- 卡片存在生成历史时禁止删除，提示“该提示词存在生成历史，无法删除”；
- 删除成功后从当前列表移除卡片，并清理对应示例图文件。

## 5. HTTP API 设计

所有接口继续使用现有 Bearer Token 鉴权。未登录或令牌失效沿用当前 401 处理和退出登录流程。

### 5.1 新增卡片

`POST /api/prompt-cards`

请求类型为 `multipart/form-data`：

- `title`：标题；
- `prompt_text`：提示词正文；
- `image_manifest`：JSON 字符串，描述最终图片顺序；
- `new_images`：按文件索引重复提交的新图片文件。

新增时清单只包含新上传图片，例如：

```json
[
  {"kind": "upload", "file_index": 0},
  {"kind": "upload", "file_index": 1}
]
```

成功返回 201 和完整的 `PromptCardItem`。分类列表为空。

### 5.2 编辑卡片

`PUT /api/prompt-cards/{card_id}`

字段与新增接口一致。编辑时清单可以混排旧图片和新图片：

```json
[
  {"kind": "existing", "image_index": 2},
  {"kind": "upload", "file_index": 0},
  {"kind": "existing", "image_index": 1}
]
```

旧图片索引必须属于当前卡片，且不能在同一清单中重复引用；新图片文件索引必须完整、有效且不能重复。未出现在清单中的旧图片视为删除。

成功返回 200 和更新后的完整 `PromptCardItem`。编辑不修改卡片既有的分类关联和 `sort_order`。

### 5.3 删除卡片

`DELETE /api/prompt-cards/{card_id}`

- 成功返回 204；
- 卡片不存在返回 404；
- 卡片存在生成历史、受外键约束保护时返回 409。

## 6. 后端组件边界

### 6.1 路由层

路由层负责：

- 鉴权；
- 解析表单和图片顺序清单；
- 将业务错误映射为稳定的 HTTP 状态码与中文错误信息；
- 返回现有 `PromptCardItem` 响应结构。

路由层不直接实现图片编排和文件替换算法。

### 6.2 卡片写入服务

新增一个聚合卡片元数据与图片文件操作的写入服务，负责：

- 校验标题和提示词；
- 校验图片数量、大小、总量、真实格式和清单引用；
- 将旧图片和新图片按目标顺序写入临时目录；
- 生成连续的正式文件名；
- 调用仓储层新增或更新数据库记录；
- 在失败时清理临时文件并恢复原文件；
- 删除成功后清理卡片图片。

该服务依赖仓储层和文件系统，不依赖 FastAPI 请求对象，便于独立测试。

### 6.3 仓储层

继续复用 `PromptCardRepository` 的新增、更新和删除能力，并补充写入服务需要的窄接口。删除时将 SQLite 外键约束错误转换为明确的“存在生成历史”业务结果，不通过字符串匹配数据库错误文本判断。

### 6.4 前端 API 层

前端 API 层增加新增、编辑、删除函数，统一构建 `FormData`，复用现有鉴权和 `ApiError` 机制。组件只传递表单状态和图片清单，不自行拼接请求 URL 或解释 HTTP 状态码。

## 7. 文件与数据库一致性

### 7.1 新增流程

1. 完成全部文本、清单和图片验证；
2. 在图片目录同一文件系统内创建临时工作目录；
3. 将图片按最终顺序写入临时目录；
4. 生成不与现有卡片冲突的文件名前缀；
5. 将临时图片移动到正式位置；
6. 在数据库事务中创建卡片；
7. 数据库失败时删除本次新建的正式图片。

### 7.2 编辑流程

1. 读取当前卡片并验证图片清单；
2. 在临时目录中按最终顺序复制旧图片、写入新图片；
3. 完成全部文件验证后，将旧图片移动到备份位置；
4. 将新图片移动到正式位置；
5. 在数据库事务中更新首图路径和图片数量；
6. 数据库失败时移除新图片并恢复备份；
7. 成功后删除备份。

文件名继续保持 `<前缀>-01.jpg`、`<前缀>-02.jpg` 或对应 PNG 后缀的连续形式。同一卡片的图片使用统一格式：最终图片全部为 JPEG 时保留 JPEG；只要最终清单中包含 PNG，就使用 Pillow 将全部图片解码并统一编码为 PNG。该规则可以保留透明通道，也避免仅修改扩展名。解码或编码失败时，请求失败且不修改原卡片。

### 7.3 删除流程

数据库删除优先执行。外键冲突时不修改图片文件。数据库删除成功后清理图片；若文件清理失败，记录错误日志，数据库删除仍视为成功，遗留文件不再被公开卡片引用，可由后续维护任务清理。

## 8. 错误处理

前端对可修正错误显示到对应表单区域，对操作级错误显示抽屉内提示。主要错误包括：

- 标题或提示词为空；
- 没有示例图；
- 文件格式、单张大小、数量或总量超限；
- 图片清单损坏或引用无效；
- 卡片不存在；
- 卡片存在生成历史，无法删除；
- 文件写入或数据库操作失败；
- 网络连接失败。

服务端响应不暴露磁盘绝对路径、SQL 内容或异常堆栈。详细异常写入现有后端日志，响应使用稳定、可面向用户展示的中文信息。

## 9. 测试策略

### 9.1 后端

- 新增单图和多图卡片；
- 编辑文本但保留原图；
- 混排旧图片和新图片；
- 删除旧图片并重新编号；
- 空标题、空提示词和零图片校验；
- 非法清单、重复索引和越界索引校验；
- 伪造扩展名、损坏图片和不支持格式校验；
- 单张大小、图片数量和总量限制；
- 数据库失败和文件失败时的清理与恢复；
- 删除无历史卡片并清理文件；
- 删除有生成历史卡片返回 409 且保留文件；
- 鉴权失败、404 和响应模型。

### 9.2 前端

- 从工具栏打开新增抽屉；
- 从卡片菜单打开编辑抽屉并回填数据；
- 必填字段和至少一张图片校验；
- 批量选择、预览、移除、拖动与按钮排序；
- 保存期间防止重复提交；
- 新增或编辑成功后更新当前列表；
- 保存失败后保留全部输入；
- 未保存修改的关闭确认；
- 删除二次确认、删除成功和 409 冲突提示；
- 401 时沿用当前退出登录行为；
- 窄屏全屏抽屉和基本键盘可操作性。

### 9.3 回归验证

执行完整后端测试、前端测试和前端生产构建，重点确认：

- 提示词库浏览、搜索、筛选、排序和预览不变；
- “使用此提示词”仍能进入生成工作台；
- 生成历史页仍能读取关联卡片；
- 现有命令行导入卡片仍能正常展示和编辑。

## 10. 验收标准

- 用户可以从提示词库新增包含标题、提示词正文和 1 至 20 张示例图的卡片；
- 用户可以编辑文本，并任意混排保留图片与新上传图片；
- 页面刷新后卡片内容和图片顺序保持正确；
- 任一保存步骤失败时，不产生可见的半成品卡片，原卡片不被破坏；
- 无生成历史的卡片可以删除，有生成历史的卡片被明确阻止；
- 所有错误信息为中文，不泄露内部路径或堆栈；
- 现有提示词浏览、生成和历史功能的自动化测试继续通过。
