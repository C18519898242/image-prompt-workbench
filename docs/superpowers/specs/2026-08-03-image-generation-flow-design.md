# 图片生成流程设计

## 1. 背景

当前生成工作台的“开始生成”按钮只显示“已创建本地生成任务（演示）”，没有调用图片模型。生成历史页面只能读取已经写入 `generation_history` 的完成图片，不了解正在生成或生成失败的任务。

本次功能复用 `C:\src\g\st-persona-generator` 的 Gemini 原生图片生成方式，让工作台真正调用 Nano Banana 2，并在发起请求后立即跳转历史页面展示临时状态。

## 2. 目标

- 点击“开始生成”后立即跳转到历史页面。
- 历史页默认筛选本次使用的提示词卡片，并保持“最新生成”排序。
- 按用户选择的生成数量串行生成图片，任何时刻最多显示一个 loading 卡片。
- 单张成功后显示正常历史卡片；单张失败后在当前浏览器会话保留失败卡片。
- 成功图片继续写入现有图片目录和 `generation_history` 表。
- 失败详情写入控制台和文本日志，不写数据库。
- 使用 Gemini 原生 API，并支持参考图、比例、分辨率和思考级别。

## 3. 非目标

- 不增加任务表、消息队列、独立 worker、定时任务或任务恢复。
- 不保证刷新浏览器后恢复 loading 或失败卡片。
- 不提供失败任务的自动重试或一键重新生成。
- 不提供跨进程任务状态同步。
- 不为个人项目引入额外的高可用架构或复杂权限系统。

## 4. 核心方案

### 4.1 临时状态归属

生成批次和临时卡片由前端 `AppShell` 保存。这样从工作台切换到历史页时，请求和状态不会因工作台组件卸载而丢失。

后端不保存 loading 或失败状态。后端每次只处理一张图片，成功后写入现有历史表并返回完整历史记录；失败时返回错误并写日志。

浏览器刷新会清空前端临时状态。已经成功并写入数据库的图片会通过现有历史 API 再次出现；尚未完成的后端请求可以继续执行，完成后也会写入历史，用户再次刷新即可看到。

### 4.2 串行生成

生成数量由前端调度，不传给单张生成接口。一个批次的执行顺序如下：

1. 创建第一个 loading 卡片。
2. 跳转历史页并发起一次单张生成请求。
3. 请求成功时把 loading 替换为成功卡片；请求失败时把 loading 替换为失败卡片。
4. 如果批次仍有效且还有剩余数量，再创建下一个 loading，并发起下一次请求。
5. 重复上述过程，直至达到用户选择的数量。

任何时刻，一个批次最多只有一个 loading 卡片。新建的 loading 使用更晚的前端时间和递增序号，因此始终显示在最前面。

### 4.3 终止旧批次

全局只调度一个当前批次，但“开始生成”按钮不会因已有批次而禁用。

用户在旧批次尚未结束时再次点击“开始生成”：

- 旧批次立即失效，不再调度后续图片。
- 移除旧批次当前的 loading 卡片。
- 已经完成或失败的旧卡片继续保留在当前会话。
- 立即创建新批次的第一个 loading，跳转历史页并开始生成。
- 已经发到后端的旧请求不强制取消，允许继续消耗模型请求并写入成功历史。
- 旧请求返回成功时，结果作为普通成功卡片显示，但不得触发旧批次的下一张。
- 不增加后端取消接口或取消标记。

## 5. 前端设计

### 5.1 批次与临时卡片

`AppShell` 保存以下概念状态：

- 当前批次 ID。
- 当前批次剩余生成数量。
- 生成所需的提示词卡片、编辑后的提示词、生成参数和参考图片文件。
- 当前会话中的临时卡片列表。

临时卡片包含客户端唯一 ID、批次 ID、提示词卡片信息、模型、比例、分辨率、创建时间、批次内序号和状态。状态只有：

- `loading`：当前单张请求尚未返回。
- `failed`：当前单张请求失败，只在当前会话保留。
- `completed`：请求返回了真实 `GenerationHistoryItem`。

批次 ID 用于判断异步结果是否仍可继续调度。旧批次的成功结果可以进入列表，但只有当前批次的结果可以创建下一张 loading。

### 5.2 工作台提交

`GenerationWorkspacePage` 不直接负责长请求，只收集并提交以下内容给 `AppShell`：

- 当前提示词卡片。
- 用户编辑后的提示词。
- 模型、比例、分辨率、生成数量和思考级别。
- 最多 8 个参考图片 `File`。

参考图状态必须保留原始 `File`，对象 URL 只用于本地预览。

点击按钮时，只要提示词非空就允许提交。若已有批次，提交动作同时使旧批次失效，然后启动新批次。

### 5.3 历史页初始化与合并

从工作台进入历史页时，`AppShell` 将本次提示词卡片 ID 传给 `GenerationHistoryPage`。页面用它初始化“提示词卡片”筛选，排序保持 `newest`。

“默认选择提示词卡片”仅表示筛选框默认选中本次卡片，不自动选择任何图片，也不自动打开右侧详情。

历史页把后端历史和当前会话临时卡片合并展示：

- 成功临时卡片如果已经带有真实历史 ID，需要与后端列表按 ID 去重。
- loading 和失败卡片同样参与提示词卡片、模型、比例、时间和搜索筛选。
- 当前会话以内置的毫秒时间和序号排序；后端历史继续按 `created_at DESC, id DESC` 排序。
- 用户手动改变筛选条件后，不再强制恢复到本次提示词卡片。

### 5.4 卡片表现

- loading 卡片显示占位区域、旋转动画和“生成中”，不能预览、下载或删除。
- failed 卡片显示失败图标、“生成失败”和“请查看后台日志”，不能预览或下载。
- completed 卡片完全复用现有历史卡片、详情、预览、下载和删除能力。

## 6. 后端接口设计

### 6.1 单张生成接口

新增受现有 Bearer Token 保护的接口：

```text
POST /api/generations
Content-Type: multipart/form-data
```

表单字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `prompt_card_id` | 整数 | 当前提示词卡片 ID |
| `prompt` | 字符串 | 用户编辑后的最终提示词 |
| `model` | 字符串 | 当前界面模型名，现阶段为 `Nano Banana 2` |
| `aspect_ratio` | 字符串 | `Auto` 或界面支持的具体比例 |
| `resolution` | 字符串 | `1K` 或 `2K` |
| `thinking_level` | 字符串 | `minimal` 或 `high` |
| `reference_images` | 图片文件数组 | 可选，最多 8 张 |

接口每次只生成一张图片。成功返回 `201` 和现有 `GenerationHistoryItem`；失败返回错误响应，不创建历史记录。

### 6.2 Gemini 配置

后端设置增加：

- `GEMINI_API_KEY`：必填的模型密钥。
- `GEMINI_BASE_URL`：默认 `https://gemini.xyz365.tech/v1beta`。
- `GEMINI_MODEL`：默认 `gemini-3.1-flash-image`。

界面中的 `Nano Banana 2` 映射到配置的 `GEMINI_MODEL`。密钥只在后端读取。

### 6.3 Gemini 原生请求

调用地址：

```text
{GEMINI_BASE_URL}/models/{GEMINI_MODEL}:generateContent
```

请求沿用参考项目的协议：

- `Authorization: Bearer {GEMINI_API_KEY}`。
- `contents[0].parts` 的第一项是最终提示词。
- 参考图片读取为字节后，以 Base64 `inlineData` 追加到 parts。
- `generationConfig.responseModalities` 为 `['IMAGE']`。
- `generationConfig.imageConfig.imageSize` 使用用户选择的 `1K` 或 `2K`。
- `aspect_ratio` 为 `Auto` 时不发送 `imageConfig.aspectRatio`，否则原样发送。
- `generationConfig.thinkingConfig.thinkingLevel` 使用 `minimal` 或 `high`。
- 不请求或展示思考过程。

后端从 Gemini 响应的 `inlineData` 或 `inline_data` 中提取第一张 PNG/JPEG，并验证 Base64 和图片内容有效。

### 6.4 单次请求重试

单张生成请求只对以下情况最多尝试 3 次，并使用简单递增等待：

- HTTP 429。
- HTTP 5xx。
- 响应不是有效 JSON。
- 响应没有可用图片。
- 图片 Base64 或图片内容无效。

401、403、其他明确的 4xx 不重试。三次仍失败时，该前端卡片进入 failed 状态。这里的重试属于一次接口调用内部的传输级容错，不会创建新的任务卡片，也不是失败后的自动重新生成。

### 6.5 图片与历史写入

生成结果写入现有 `data/generated-images/`，文件名使用时间和随机标识避免冲突，并根据 Gemini 返回的 MIME 类型选择扩展名。

写入顺序：

1. 把图片写到目标目录中的临时文件。
2. 原子替换为最终文件。
3. 调用现有 `GenerationHistoryRepository.create_history` 写入历史。
4. 返回新建的历史记录。

如果历史写入失败，删除本次新建图片，避免留下无法从历史页管理的孤立文件。

## 7. 日志与错误表现

使用 Python 标准 `logging`，同时输出到后端控制台和 `data/logs/app.log`。不引入独立日志服务。

日志包含：

- 提示词卡片 ID。
- Gemini 模型。
- 比例、分辨率和思考级别。
- 当前尝试次数。
- HTTP 状态或异常堆栈。

日志不写 API Key 和参考图 Base64。接口只向前端返回简短错误信息，失败卡片统一提示用户查看后台日志。

## 8. 测试设计

### 8.1 后端

- 验证 Gemini URL、Bearer 头和请求体。
- 验证提示词和多张参考图的 `inlineData`。
- 验证 `Auto` 不发送比例，其他比例正常发送。
- 验证 `1K`、`2K` 和 `minimal`、`high` 映射。
- 验证 PNG/JPEG 提取和无效图片拒绝。
- 验证 429、5xx、无效响应的重试，以及不可重试 4xx。
- 验证成功写图片和历史，并返回历史记录。
- 验证失败不写历史且产生日志。

### 8.2 前端

- 点击后立即跳转历史页并默认筛选当前提示词卡片。
- 数量大于 1 时始终只有一个 loading，并串行调用接口。
- 单张结束后才创建下一张 loading。
- loading、失败和成功卡片按最新时间显示在最前面。
- 成功临时卡片与后端历史按 ID 去重。
- 再次提交会终止旧批次的后续调度、移除旧 loading 并启动新批次。
- 旧批次已发出的请求成功后仍显示结果，但不继续旧批次。
- loading 与失败卡片正确参与筛选，且没有图片操作。

自动测试使用与 Gemini 原生响应结构一致的模拟数据，不调用真实模型。最终验证运行后端完整测试、前端完整测试和前端生产构建。真实 API 调用仅作为可选人工冒烟测试。

## 9. 验收标准

- “开始生成”不再显示演示反馈，而是真正调用 Gemini。
- 跳转历史页后默认选中本次提示词卡片筛选。
- 最新的 loading、失败或成功卡片显示在列表最前面。
- 一个批次中任何时刻最多显示一个 loading。
- 生成数量为 2 或 4 时，调用严格串行。
- 单张失败不会阻止当前批次继续生成下一张。
- 再次提交会停止旧批次后续图片并启动新批次。
- 成功图片在刷新后仍可见；loading 和失败卡片刷新后消失。
- 后端控制台和 `data/logs/app.log` 可以定位生成失败原因。
